# 실행 방법
## 1. 환경 준비

| 항목 | 설정 |
|---|---|
| 최소 실행 버전 | Android API 26 |
| compileSdk / targetSdk | 37 / 37 |
| Android Gradle Plugin | 9.4.1 |
| Gradle Wrapper | 9.6.0 |
| Kotlin 플러그인 버전 | 2.2.10 |
| Gradle Daemon JVM | JDK 25 |
| 앱 Java 컴파일 대상 | Java 17 |

## 2. `local.properties` 설정

프로젝트 **루트**의 `local.properties`를 열어 다음 항목을 추가합니다.

```properties
UNSPLASH_ACCESS_KEY=YOUR_UNSPLASH_ACCESS_KEY
```

`YOUR_UNSPLASH_ACCESS_KEY`를 실제 Unsplash에서 발급받은 **Access Key**값으로 교체합니다. **따옴표나 `Client-ID` 접두사를 붙이지 않고 키 값만 입력**합니다. 
설정 이름은 대소문자를 포함해 `UNSPLASH_ACCESS_KEY`이며, `access_key`는 사용하지 않습니다.

키는 Gradle에서 `BuildConfig.UNSPLASH_ACCESS_KEY`로 주입하며, API 클라이언트가 `Authorization: Client-ID ...` 헤더를 구성합니다. 
**키를 변경한 뒤에는 다시 빌드해야 합니다.** 현재 빌드 스크립트는 이 값을 `local.properties`에서 읽으며, 환경 변수나 `gradle.properties`만 설정하는 방식은 구현하지 않았습니다.

> **테스트 실행 전에도 키 설정이 필요합니다.** API 테스트는 MockEngine을 사용하지만, 현재 빌드 스크립트는 Gradle 구성 단계에서 키의 존재를 검사합니다.

# 주요 설계 결정
## 페이지 간 중복 사진은 유지하고, 화면 항목 키를 분리

실제 API 응답을 20페이지까지 확인했을 때 총 400개 항목 중 21개가 반복되어, 해당 탐색에서는 약 5.25%의 중복이 관찰되었습니다.(다른 시점의 응답에서도 같은 비율을 보장한다는 의미는 아닙니다.)

중복 제거 방식도 구현하여 비교한 결과, 중복 ID/성공 페이지 결과 관리 외에도 연속된 페이지가 전부 중복인 경우에 탐색 중단/재개를 위한 추가 상태 관리가 필요했습니다.
이를 근거로 중복 제거 방식은 반복 노출을 줄이는 이득에 비해 구현과 검증 비용이 높다고 판단했습니다.

최종 구현은 **API 응답의 항목과 순서를 유지**합니다. 동일 사진이 여러 번 나타나더라도 목록 키가 충돌하지 않도록 `페이지 번호 + 페이지 내부 위치 + 사진 ID`로 합성 키를 부여합니다.
사진의 좋아요/파일/상세 조회에는 합성 키가 아니라 기존 `photo.id`를 사용합니다.

최신순은 `Get /photos`의 응답 순서를 따르고, 클라이언트에서 `created_at`이나 `updated_at`으로 다시 정렬하지 않습니다.

[Unsplash 목록 정렬 변경 안내](https://unsplash.com/documentation/changelog#removal-of-order_by-from-get-photos)

## 좋아요 선택과 오프라인 준비 상태 분리
좋아요 선택은 다운로드 전에 Room에 저장합니다. `favorite_photos`에는 선택과 사진 정보를, `photo_files`에는 요청 ID/상태/상대 파일 경로를 관리합니다.
> 좋아요 여부와 오프라인 파일 준비 상태는 별도로 관리합니다. 좋아요 목록에는 파일 저장이 완료된 사진만 표시합니다.

| 파일 상태 | 의미 | 좋아요 목록 노출 |
|---|---|---|
| `PENDING` | 다운로드 대기/진행/재시도 대기 | 제외 |
| `READY` | 앱 내부 파일 저장 완료 | 로컬 파일 경로가 있는 항목 표시 |
| `FAILED` | 다운로드 요청 처리가 최종 실패 | 제외 |

다운로드 실패만으로 좋아요를 취소하지 않도록 했습니다. Feed와 상세는 같은 사진 ID의 DB 상태를 관찰하며, 좋아요 목록은 과제 요구사항에 맞춰 **저장이 완료된 사진만** 보여줍니다.
다운로드 재시도는 상세 화면에서 제공하고, Feed에는 별도 재다운로드 버튼을 두지 않았습니다.

## 파일 관리와 작업 수명

좋아요한 사진은 **앱 내부 저장소(`filesDir/favorites/`)에 파일로 저장**하고, 저장이 완료되면 **해당 파일의 상대 경로를 로컬 DB에 기록**합니다.

WorkManager는 네트워크 조건과 재시도/취소를 관리합니다. 현재 작업 체인은 **다운로드 이벤트 보고 -> 이미지 다운로드** 순서이며, 보고 단계가 최종 실패하면
후속 이미지 다운로드도 진행하지 않습니다. 
이미지 파일 저장 후에는 현재 `requestId`가 유효한 경우에만 결과를 반영합니다.
> **requestId(다운로드 요청 식별자)**
> `requestId`는 다운로드 결과가 현재 유효한 요청에 속하는지 확인하기 위한 식별자입니다.
> 좋아요를 해제하면 해당 요청의 취소를 시도하고, 다시 등록하면 새로운 요청 ID를 사용합니다.
> 이 식별자는 **이전 다운로드의 처리 결과가 현재 다운로드의 상태를 잘못 변경하는 것을 방지**하기 위해 사용합니다.
> 예를 들어 다음 상황이 발생할 수 있습니다.
> ```text
> 사진 A 좋아요 등록 -> r1 다운로드 시작
> 좋아요 해제 후 A 재등록 -> r2 다운로드 시작 및 완료
> 뒤늦게 r1 결과가 실패 반환 -> `reqeustId`가 없는 경우 정상적인 r2 요청 완료가 r1의 실패로 반영 됨
> ```

삭제할 경로는 `pending_file_deletions`에 남겨 별도로 정리합니다. 좋아요 해제와 실제 파일 삭제가 반드시 같은 순간에 완료되지는 않습니다.
